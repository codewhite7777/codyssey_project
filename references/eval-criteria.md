# Codyssey 평가 채점 패턴 — 역설계 정리

> 출처: `~/Desktop/eval_pdf/` 의 타인 평가 참여 자료 6건 (평가 기준 참고용).
> 탐험가명은 타인이며 본인 제출물이 아니다. **채점 구조를 읽기 위한 자료**로만 쓴다.

## 2. 평가지 공통 구조

모든 미션의 평가지가 동일한 5항목 골격을 쓴다.

| 항목 | 성격 | 묻는 것 | 대비 방법 |
|---|---|---|---|
| **항목 1** | 동작 검증 | "…가 정상 동작하는가?" | 기능 구현 + 실행 증거 |
| **항목 2** | 구현 설명 | "…를 **어떻게** 구현했는지 설명할 수 있는가?" | 설계 결정 로그 |
| **항목 3** | 개념 설명 | "…원리를 설명할 수 있는가?" | 개념 카드 |
| **항목 4** | 확장·응용 | "만약 …라면 어떻게 하겠는가?" | 가정 질문 사전 답변 |
| **항목 5** | 보너스 | 크레딧 부여/미부여 (100점) | 선택 과제 수행 |

## 3. 가장 중요한 관찰

**항목 1을 PASS하고도 전체 FAIL이 난다.**

`b2-1_eval.PNG`가 결정적 사례다.
- 항목 1 (add/list/search/export/import/update/delete 동작, CSV 스키마, 오류 처리) → **PASS**
- 항목 2 (모듈을 "어떻게" 나눴는지, 클래스 책임 경계를 "어떻게" 정했는지) → **FAIL**
- 항목 3 (제너레이터 스트리밍을 "왜" 유리하게 썼는지, 데코레이터 분리 이유) → **FAIL**
- 항목 4 (JSONL vs CSV 선택 근거, 10만 건일 때 병목) → **FAIL**

즉 **코드는 돌아갔지만 설계 근거를 말하지 못해서 떨어졌다.**
평가 결과란의 `경험정도: 재구현 불가`가 이 상태를 가리킨다.

→ 이것이 `SPEC.md` 제1 원칙("설명할 수 없는 코드는 미완성이다")과
   §4 주석 규약에서 `WHY:`에 **기각한 대안**을 강제하는 이유다.

## 4. 항목별 질문 어휘 패턴

구술 질문은 아래 어휘로 반복된다. 노트를 쓸 때 이 어휘에 맞춰 답을 준비한다.

- **"어떻게"**: 사용한 명령/도구/자료구조와 **선택 이유**를 함께 요구한다.
  예) "프로세스 식별(pgrep/ps 등)과 포트 확인(ss/netstat 등)에 사용한 명령과 **선택 이유**"
- **"왜"**: 설계의 정당화를 요구한다.
  예) "api_keys를 agent-core로 제한한 이유를 **최소 권한 원칙**으로 설명"
- **"만약 ~라면"**: 확장·장애 시나리오.
  예) "데이터가 10만 건으로 늘어나면 병목은 어디이며 어떻게 개선하는가"
  예) "LRU 대신 LFU를 구현한다면 자료구조를 어떻게 바꾸는가"
  예) "모니터링 대상이 Nginx로 바뀐다면 monitor.sh에서 바꿔야 할 핵심 포인트"
- **"판단 흐름"**: 순서와 근거를 요구한다.
  예) "살아있지만 멈춰있는 상태를 진단하기 위해 어떤 도구를 **어떤 순서로** 사용했는지"
- **"다시 한다면"**: 거의 모든 미션의 마지막 질문.

## 5. 증거 요구 수준

리포트/문서형 산출물은 증거의 **최소 요건**이 명시된다. 공통적으로 요구되는 것:

- PID, 로그 타임스탬프, 핵심 로그 메시지
- 조치 전후 **Before & After 비교** (수치 또는 스크린샷)
- 사용한 명령어와 옵션 (옵션의 의미를 구분해 서술할 수 있어야 함)
- 구조 고정: 현상 → 증거 → 원인 → 조치

## 6. 보너스

- 별도 크레딧 100점. 부여/미부여 단일 판정.
- 관찰된 보너스 유형: 요약 리포트 스크립트(`report.sh`), 시간 기반 로그 보존 정책,
  로그 패턴으로 스케줄링 알고리즘 역추론.
- **미수행도 기록한다.** 수행 여부 판단 자체가 진도 관리 정보다.
